# Story 15.3: Multi-domain search

## Status: Draft

## Story

**As an** AD operator,
**I want** the search bar in the lookup pages and the deep-link `get_user_by_identity` (used by Epic 3 user comparison, Epic 4 group browsing, etc.) to find objects in any domain of the forest,
**so that** I can locate an object by sAMAccountName, UPN, or display name without knowing which domain hosts it.

## Acceptance Criteria

1. The five backend `search_users` / `search_computers` / `search_groups` / `get_user_by_identity` / `get_group_members` functions on `DirectoryProvider` are wrapped at the `ForestProvider` level to fan out to every partition.
2. `search_*` results are merged with the same logic as Story 15.2 (sorted, partition-tagged, partial-failure tolerated).
3. `get_user_by_identity(sAMAccountName)` is documented as ambiguous in a multi-domain forest. New contract: the function returns *the first match* (seed partition wins on ties); a new `find_users_by_identity_across_forest(sAMAccountName) -> Vec<DirectoryEntry>` returns every match. The single deep-link callsite in `UserLookup.tsx` consumes the disambiguating variant when more than one match is found and opens a small chooser dialog.
4. `get_group_members` continues to expand only group members of the same partition; foreign security principals (members from a different domain in a cross-domain group) are returned as their FSP DN in `CN=ForeignSecurityPrincipals,...`. The frontend resolves the SID -> object via a cross-partition lookup using the existing `services::sid_resolution` helper, extended to consult every partition.
5. Server-side search input validation (`validate_search_input` in `services/ldap_directory.rs`) is unchanged - per-partition queries reuse the same sanitizer.
6. Unit tests cover (a) the multi-match disambiguation path returning a sorted vec, (b) the FSP cross-partition resolution, (c) the partial-failure case where one partition errors and the search still returns the matches from the others.

## Dev Notes

### Identity disambiguation in real forests

In a forest with `corp.example.com` and `eu.corp.example.com`, a `jdoe` sAMAccountName can exist in both partitions. The existing single-domain code returned `Option<DirectoryEntry>` and the consumer (deep-link from User Comparison, group member click-through, etc.) opened the user detail directly. Story 15.3 keeps the `Option` shape for the legacy callsite (always returns *something*) but adds a list-returning variant for callers that need to handle the multi-match case.

The chooser dialog avoids automatic disambiguation: there is no foolproof rule (which `jdoe` is "the right one"?), so the operator picks. The dialog is small enough to skip when there's exactly one match.

### Foreign security principals

In a cross-domain group membership, the `member` attribute of the group holds the DN of the user *as known by the group's partition*. For a user from another domain, AD writes a `CN=<SID>,CN=ForeignSecurityPrincipals,<group's partition DN>` entry. To display the actual user, DSPanel must resolve the SID against the user's own partition.

The resolution path is straightforward: extract the SID from the FSP DN (the CN is the SID in string form), iterate the partitions calling `search_*` with `(objectSid=<sid>)`, return the first hit. Cache the SID -> entry mapping for the session to avoid re-resolving on every group member render.

### Project structure note

Search fan-out lives next to browse fan-out in `services/forest_browse.rs` (or a new `services/forest_search.rs` if the file grows past ~400 lines). The FSP resolver lives in the existing `services/sid_resolution.rs`.
