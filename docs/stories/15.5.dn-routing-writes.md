# Story 15.5: DN-based routing for write commands

## Status: Draft

## Story

**As an** AD operator with the right permission level,
**I want** every write command (password reset, account enable / disable / unlock, group membership add / remove, attribute modify, move, recycle-bin restore, the three Epic 14 quick-fixes, the onboarding and offboarding workflows of Epic 5) to be routed to the partition that owns the target DN,
**so that** I can administer any object in the forest without DSPanel silently writing to the wrong partition or returning a `referral` it cannot follow.

## Acceptance Criteria

1. Every write command in `commands/account.rs`, `commands/group.rs`, `commands/cleanup.rs`, `commands/security.rs` (Epic 14 quick-fixes), `commands/onboarding.rs`, `commands/offboarding.rs`, `commands/recycle_bin.rs` MUST call `state.forest().route_for_dn(target_dn)?` as the first line of its handler before any LDAP write. Cross-partition write fan-out is NOT supported - each write affects exactly one partition.
2. Group membership across partitions: when adding a user from partition A to a group in partition B, the **group's** partition is the one written to (Microsoft's convention: a group's `member` attribute holds the DN of any forest object). Routing uses the group DN, not the user DN.
3. Move-object across partitions is explicitly rejected with a typed error `AppError::CrossPartitionMoveNotSupported`. The frontend `MoveObjectDialog` filters the OU picker to the same partition as the source. The cross-partition rejection error message uses i18n key `forest.crossPartitionMoveNotSupported` translated in EN/FR/DE/IT/ES, surfaced in the move dialog and as the `AppError::CrossPartitionMoveNotSupported` user-facing message.
4a. Audit annotation: every audit entry written by Epic 14 quick-fixes, Epic 2 password operations, Epic 4 group operations, Epic 5 onboarding/offboarding, Epic 7 object management gets a `partition_dns_name: Option<String>` field populated from the routing decision. The field is added to `AuditEntry`, persisted as a nullable column on the `audit_log` SQLite table, indexed for filtering, and serialized into the syslog payload (Story 15.6 AC #4 spells the SD-ID/SD-PARAM shape). **The chain hash excludes `partition_dns_name` unconditionally**, matching the Epic 14 `severity` precedent (verified in `services/audit.rs::compute_hash` and the existing `test_severity_excluded_from_hash_chain` regression test). This guarantees that pre-1.2.0 chains stay valid byte-for-byte and that the new field is operational metadata, not audit truth.
4b. Snapshot annotation: the snapshot service persists the source partition with each snapshot via a new nullable `partition_dns_name` column on the snapshot table. Restore routes via `ForestProvider::route_for_dn(snapshot.partition_dns_name)` when the column is non-null, falling back to the seed partition when null (legacy snapshots). When the source partition recorded in a snapshot is currently `Unreachable` at restore time, the restore is rejected with `AppError::PartitionUnreachable(partition_dns_name)` and a translated user-facing message. The operator must wait for the partition to recover (or use the Story 15.6 retry control) before restoring. We do NOT silently fall back to a different partition - that would corrupt the audit trail.
5. Permission gates (`require_permission`, `require_fresh_permission`) are evaluated *per partition* against the operator's group memberships in that partition. Cache key on `services/permissions.rs` becomes `(identity, partition_dns_name)` (was `(identity)`). TTL is unchanged. The `require_fresh_permission` invalidation path purges only the cache entries for the target partition, not the whole cache. A `DomainAdmin` of `corp` is NOT automatically a `DomainAdmin` of `corp-east`; the well-known-RID lookup is run against the target partition's connection.
6. Unit tests cover (a) the group-membership routing rule with a user in A added to a group in B, (b) the cross-partition move rejection, (c) the per-partition permission gate (a user with admin rights in only one partition gets `PermissionDenied` when targeting another), (d) audit and snapshot annotation with `partition_dns_name`.
7. Risk register: this story is the highest-blast-radius story of Epic 15. It touches every write command, the audit hash chain, the snapshot table, and the permission cache. The audit chain integrity test fixture (Story 15.6 AC #8) MUST pass before this story can be marked Done. The audit-security skill SHOULD be run on the implementing PR.

## Dev Notes

### Why the group's partition wins

LDAP `member` is a DN-valued attribute on the group object. The DC writing to the group does NOT need to know about the member's partition; AD replication propagates the FSP entry into the group's partition (under `CN=ForeignSecurityPrincipals`) when the member is from another domain. Routing the write to the group's partition is the only correct choice; routing to the member's partition would produce a `noSuchAttribute` because the member object doesn't host a back-link `memberOf` that we can edit (it's a constructed attribute).

### Cross-partition move is genuinely hard

A real cross-partition move uses `ldap_modify_dn` against a DC that's a GC of both partitions, and on Windows it is implemented by repadmin / dsmove with extra plumbing (NTDS quota check, password reset to force a new salted hash on the target side, replication wait). DSPanel doesn't have the safety net to do that reliably; rejecting at the UI is the right v1.2.0 call.

### Per-partition permission gate

A `DomainAdmin` group exists *per domain*. The same operator may be `DomainAdmin` of `corp` and a regular user in `corp-east`. The current `services/permissions.rs::detect_permission_level` runs against the bound DC (one partition). For multi-partition writes, we need to detect the level *against the target partition's DC*. The mapping is straightforward because each partition has its own connection in the `ForestProvider`; we just call `detect_permission_level(target_partition_provider)` once per partition and cache the result.

### Project structure note

The cross-partition rejection error variant lives in `src-tauri/src/error.rs` next to the existing `AppError::PermissionDenied`. The migration files live under `src-tauri/migrations/` (rusqlite-bundled migration pattern, mirror Epic 11 + Epic 14 precedents).

### Why exclude partition_dns_name from the hash chain unconditionally

The Epic 14 `severity` column established the precedent: a column added by a non-destructive migration that carries operational metadata (not audit truth) is excluded from the chain hash unconditionally so existing chains remain valid byte-for-byte across the upgrade. The implementation lives in `services/audit.rs::compute_hash` (lines 385-395) and is locked in by the `test_severity_excluded_from_hash_chain` regression test. The doc comment above `compute_hash` calls out the rationale: chain protects audit truth (operator, action, target, success); operational categorisation hints (severity, partition) are out.

`partition_dns_name` is the next column to follow that pattern. Including it conditionally (in the hash for post-1.2.0 entries, out of the hash for pre-1.2.0 NULLs) would create two parallel chain semantics and complicate every future migration. Excluding unconditionally:

- keeps the chain definition stable: hash inputs are `(timestamp, operator, action, target_dn, details, success)`, full stop.
- preserves backward compatibility: pre-1.2.0 chains stay valid, no re-hash, no re-sign.
- treats partition as the operational metadata it is: same operator, same target DN, same action -> same audit truth, regardless of which DC happened to write it.

The matching regression test goes alongside the severity one in `services/audit.rs::tests`.
