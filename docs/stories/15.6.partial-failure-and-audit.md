# Story 15.6: Partial-failure UI and audit tagging

## Status: Draft

## Story

**As an** AD operator,
**I want** a clear, non-blocking signal when one or more domains in the forest are temporarily unreachable, with a per-partition retry control,
**so that** I know my view is partial, can fix the network or DC issue, and can refresh the affected partition without having to relaunch DSPanel.

## Acceptance Criteria

1. A new `<ForestStatusBanner>` component lives **under** the Sidebar at the top of the main content area (matches existing connection error banner placement, see `Sidebar.tsx`) and renders only when `ForestProvider::partition_status()` reports at least one partition as `Unreachable` or `Reconnecting`. The banner lists the affected partitions with their last classification key (e.g. `network`, `auth_denied`, `kerberos_unknown`) translated to the operator's language.
2. Each affected partition row carries a "Retry" button that invokes a new `forest_retry_partition(dns_name)` Tauri command, which calls `LdapDirectoryProvider::invalidate_connection` plus `test_connection` on the matching partition. The Retry button uses the secondary action button styling from `.claude/rules/dspanel-frontend.md` (with explicit border / bg / hover; never plain `btn btn-sm`). The button is disabled while a retry is in flight to prevent rapid-click double-fires; backend `forest_retry_partition` debounces by ignoring calls received within 1 second of the previous call for the same partition.
3. The lookup pages' inline `failedPartitions` warning (Story 15.2) is dismissable per session but reappears on the next `browse` or `search` if the partition is still down.
4. Every audit entry now carries a `partition_dns_name: Option<String>` column (introduced in Story 15.5 AC #4a). The syslog forwarder serializes the field as RFC 5424 SD-PARAM `partition` inside the SD-ELEMENT `dspanel@53432` (where `53432` is the IANA-pending DSPanel Private Enterprise Number; for the moment we use `dspanel@local` and document the migration path). **The audit hash chain excludes `partition_dns_name` unconditionally**, matching the Epic 14 `severity` precedent. Existing chains stay valid byte-for-byte across the upgrade.
5. The `AuditLog` page gains a "Domain" filter dropdown alongside the existing operator / action / date filters. The dropdown values are derived from the distinct `partition_dns_name` values present in the table. Filter implementation: the dropdown values come from a union of (a) live `<ForestContext>::forestTopology.partitions[].dnsName` (current partitions, reflects ongoing topology) and (b) `SELECT DISTINCT partition_dns_name FROM audit_log WHERE partition_dns_name IS NOT NULL` cached for 60 seconds (historical partitions, including any that have been decommissioned). The cache invalidates when a new audit row is written. This avoids a full-table scan on every filter open.
6. Existing audit entries (written before 1.2.0) have NULL `partition_dns_name` and the AuditLog table renders the column as `-` with a `<Tooltip>` (1.1.1 standard, never native `title`) reading 'Pre-1.2.0 entry, partition not recorded'. Backward compatibility of the chain is preserved by the unconditional hash exclusion of the new column (AC #4 above and Story 15.5 AC #4a).
7. Frontend unit tests cover (a) the banner rendering only when at least one partition is degraded, (b) the per-partition retry call, (c) the AuditLog filter dropdown deriving its values from the persisted entries.
8. Backend unit tests cover the audit table migration (adding the nullable column with index), the syslog payload serialization, and the chain-hash backward compatibility (a chain whose tail is pre-1.2.0 stays valid after the column is added).
9. Banner accessibility: the `<ForestStatusBanner>` is announced via `aria-live="polite"` when partitions transition to Unreachable, focusable via Tab, and dismissable per session via the keyboard (Esc on focused dismiss control). The dismissal does NOT clear underlying partition status; it is purely UI.
10. Capability allowlist: add `forest_retry_partition` AND `get_forest_topology` (introduced in Story 15.1 for the `<ForestContext>`) to the relevant `src-tauri/capabilities/*.json` with a one-line justification. Both are read-only / connection-state commands and require no filesystem or network scope expansion.

## Dev Notes

### Why the banner is dismissable per session, but reappears

The dismissal preserves operator focus during a known transient outage (a remote DC rebooting, a VPN flap), without forcing the operator to ack on every browse. Reappearance on next `browse` if the partition is still down keeps the operator informed: a long-lived outage isn't silenced.

### Audit chain hash backward compatibility

The pattern from Epic 14's `severity` column applies: the new field is part of the hash for entries that have it (post-1.2.0), and excluded for entries that don't (pre-1.2.0, NULL value). This keeps existing chains valid and makes the upgrade non-destructive. Document the rule in `services/audit.rs::compute_hash` with an inline comment near the `if entry.partition_dns_name.is_some()` branch.

### Why a Tauri event for status updates

Polling `partition_status` from the React side every 10s works but adds noise. The Tauri event `forest-status-changed` is emitted by the backend whenever a partition transitions (Connected -> Unreachable, Unreachable -> Reconnecting, Reconnecting -> Connected); the frontend subscribes once via `listen('forest-status-changed', ...)` and re-renders. Cheaper, more responsive.

### Project structure note

The banner lives in `src/components/common/`. The retry command and event live in `src-tauri/src/commands/forest.rs`. The new context lives in `src/contexts/ForestContext.tsx` (also created in Story 15.4 if not already there - whichever lands first). The migration migrates the audit table only; the snapshot table migration is in Story 15.5.
